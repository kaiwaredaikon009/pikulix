# 設計と調査の記録

> 開発用の作業ノートである（[docs/dev/README.md](README.md)）。Pikulix を使うだけなら、読む必要はない。使い方は [README](../../README.md) と [スクリプトの書き方](../api.md) にある。

仕様、技術方針、設計上の検討事項と、調査や確認で分かったことをまとめる。開発の進み具合と、作成者に判断や確認をお願いしていることは `docs/dev/ロードマップ.md` に、スクリプトの書き方（利用者向け）は `docs/api.md` にある。

方針が変わったとき、新しく分かったことがあるときは、このファイルを更新する。

## 技術方針（作成者承認済み）

### 構成

- **スクリプト言語は mruby**（組み込み用の Ruby 実装、MIT ライセンス）。ホストの exe に静的リンクする。
  - 本物の Ruby 構文で書け、`.rb` としてエディタの支援も受けられる。DSL を自作する必要がない。
  - 最新の安定版は mruby 4.0.0（2026-04-20 リリース）。バージョンは固定して取り込む。
- **ホストは C++**（C++17 程度）で、Win32 API を直接呼ぶ。
- **ツールチェーンは MSYS2 UCRT64 の gcc**。静的リンク（`-static`）で単一の exe にする。
  - mruby 自体のビルドに Ruby（rake）が必要なので、プロジェクトのビルドも `Rakefile` にまとめる。
- **対象は x64 のみ**。Windows 11 に 32bit 版はなく、ARM64 版は x64 エミュレーションで動く。
- **重い依存は足さない**。テンプレートマッチングは自前で実装する。OpenCV は使わない（実測と実機での確認を経て、作成者が決めた。後述）。

### 見送った案

| 案 | 見送った理由 |
| --- | --- |
| CRuby を zip に同梱する | 完全な Ruby が使えるが、数十 MB のディレクトリ一式になり「exe 1 個」から離れる。単一 exe 化するツール（ocran など）は実行時に Temp へ展開するので、要件に反する。 |
| .NET Framework 4.8 と C# | Windows 11 に標準搭載なのでランタイム不要だが、Ruby ライクにするには開発の停滞した IronRuby に頼ることになる。 |
| .NET 8 以降の自己完結型 exe | サイズが大きく、スクリプト言語の問題も解決しない。 |
| C#（.NET）のホストに mruby を組み込む | C# は C++ より書きやすい。しかし mruby は C のライブラリなので、gcc でのビルドも結局必要で、道具立てが二重になる。単一 exe にまとめる方法（Native AOT）には MSVC のリンカも要る。 |
| PowerShell のモジュールにする | 素の Windows にある言語だが、Ruby ライクでなく、実行ポリシーにも阻まれやすい。 |
| Rust や Go と独自 DSL | 言語処理系を自作するコストが高く、エディタの支援もない。 |

mruby の採用が技術検証（Phase 0）で行き詰まった場合は、CRuby 同梱案を次の候補とする。

### mruby を使ううえでの制約

利用者に見える制約なので、README にも書く。

- CRuby の gem や標準ライブラリは使えない。使える機能は、ビルドに含めた mrbgems で決まる。
- `require` は標準では無い。複数ファイルに分けたい需要が出たら、`require_relative` 相当を自前で用意する。
- エラー時にはファイル名と行番号が出る。スクリプトを書く人にとって必須である。実行時に読む `.rb` については、ファイル名をコンパイラに渡すだけで出る（`conf.enable_debug` は要らない。これは最適化を切ってしまう）。
- `File`、`Dir`、`$stdout` は使えない（次項の理由で `mruby-io` を含めていない）。テキストの読み書きだけ、自前の `read_text` などで行う（「Phase 1 で決めたこと」参照）。

### Phase 0 で分かったこと

- **取り込み方**: mruby は `git clone` でタグ `4.0.0` を `vendor/mruby` に取得し、コミットのハッシュを照合する。リポジトリにはコミットしない。パーサは生成済みのものが同梱されており、bison は要らない。
- **mrbgems**: `stdlib`、`stdlib-ext`、`math`、`metaprog` の各 gembox を含めている。
- **`mruby-io` は含めない**。Windows 用の実装（`hal-win-io`）が Winsock（ネットワーク用の `WS2_32.dll`）をリンクし、起動時に初期化するためである。画面キャプチャと入力送信をする exe がネットワークの DLL まで読み込むと、誤検知を増やすおそれがある。
- **`puts` はホストで定義している**。mruby 4.0 では、コアにあるのは `print` と `p` だけで、`puts` は `mruby-io` に含まれる。`src/prelude.rb` に Ruby で書いた定義を持ち、起動時に読み込む。`sleep` と `exit` も同じである（それぞれの mrbgem は含めていない）。
- **文字列は UTF-8 として扱う**（`MRB_UTF8_STRING`）。既定ではバイト列の扱いで、`"こんにちは".size` が 15 になる。この定義は、`mruby_build_config.rb` と `Rakefile` の両方に書く。
- **コンソールへの出力**: コアの `print` は、出力先がコンソールなら UTF-16 に変換して書く（文字化けしない）。一方、mruby のエラーメッセージは UTF-8 のバイト列のまま標準エラーへ書かれる。そのため、実行中だけコンソールの出力コードページを UTF-8 にし、終了時に戻している。緊急停止と Ctrl+C のときにも戻す（Phase 1 で対処した）。
- **mruby の例外は `longjmp`**。mruby の API が例外を投げると、C++ のデストラクタが呼ばれないまま関数を抜ける。そのため、mruby から呼ばれる C++ の関数は、決まった形で書く（`src/api.cpp` の冒頭に書いてある。引数を受け取る → C++ の処理は別の関数で行う → 失敗していたら例外を投げる）。キーワード引数の解釈など込み入ったことは Ruby 側（`src/prelude.rb`）で行うので、C++ 側は単純に保てている。
- **依存 DLL** は、UCRT（`api-ms-win-crt-*.dll`）、`KERNEL32.dll`、`USER32.dll` に、Phase 1 で `GDI32.dll`（画面キャプチャ）、`SHELL32.dll`（アプリの起動）、`ole32.dll`（COM）が加わった。どれも Windows 標準である。`Rakefile` の `ALLOWED_DLLS` に無い DLL に依存すると、ビルドが失敗する。

### Phase 1 で決めたこと

実装しながら決めたこと。作成者の判断を待っているものは、`docs/dev/ロードマップ.md` の「未決定事項」に挙げてある。

- **スクリプト API は 2 層にした**。C++（`src/api.cpp`）は `Pikulix._find` のような単純な関数だけを用意し、`find` や `click` など利用者が呼ぶメソッドは、それらを組み合わせて Ruby（`src/prelude.rb`）で書く。待ちながら繰り返し探す処理、引数の確認、ログは Ruby 側にある。`src/prelude.rb` は、ビルド時に C++ の配列に変換して exe に埋め込む。
- **画像の読み書きは WIC**（Windows 標準の画像の部品）で行う。外部のライブラリを足さずに済み、ライセンス表記も増えない。実体の `windowscodecs.dll` は実行時に読み込まれるので、依存 DLL の一覧には出ない。
- **一致度は、正規化相互相関そのものではない**。コントラストの違いと、平均の色の違いを加味した値にした（定義は `src/match.cpp` の冒頭）。正規化相互相関だけでは、有効なボタンと無効なボタン、青いボタンと灰色のボタンを区別できないためである。単色の画像も、同じ式で扱える。
- **探索は、縮小した画像どうしを比べる方式ではない**。ぼかした値を間引いた点（100 点前後）で比べる粗い探索を、すべての場所について 1 画素ずつ行い、残った候補だけを全画素で判定する。縮小の格子と位置がずれて見落とす、ということが起きない。小さな画像では、総当たりの結果と一致することをテストで確かめている。
- **実測の結果、自前実装で足りる**。フル HD の画像で 1 回の探索は 20〜40 ms だった（`rake bench`。全面が文字、全面がでたらめな模様、という意地の悪い画面でも同じ）。目安の 0.2〜0.3 秒を大きく下回る。スレッドも、CPU ごとの専用の命令（AVX など）も使っていない。OpenCV は要らない見込みである。
  - 実機でも、画像はよく見つかった（2026-11-17、手順書のテスト 3。一致度 0.998〜1.000、1 回 20〜48 ms。表示倍率 150% でも見つかった）。これを受けて、**自前実装のままとすることを作成者が決めた**（2026-11-17）。
- **緊急停止は、プロセスを即座に終了する**（`TerminateProcess`）。専用のスレッドが Alt+Shift+C を待ち、押されたら、押したままのキーとマウスボタンを離してから終了する。スクリプトが Ruby だけの無限ループに入っていても止まる。そのかわり、スクリプトの `ensure` は実行されない。
- **緊急停止のホットキーを登録できなかったときは、入力を送らない**（例外にする）。止める手段が無いまま操作するのは危険だからである。別の Pikulix が実行中のときなどに起きる。画像を探すだけ、出力するだけのスクリプトは、そのまま動く。
  - 実機でも、作りどおりに動いた（2026-11-17、手順書のテスト 8）。Pikulix を 2 つ同時に動かすと、あとから起動したほうはマウスを動かさずに終わり（終了コード 1）、先に起動したほうは Alt+Shift+C で止まった。
  - **このままとすることを、作成者が決めた**（2026-11-17）。別の常駐ソフトが Alt+Shift+C を使っている端末では操作できなくなるが、緊急停止のキーを設定で変えられるようにする、といった対処はしない。
- **コンソールの最小化は、最初に画面を写し取るか、入力を送るときに行う**。起動直後ではない。画面を使わないスクリプト（とテスト）で、端末が最小化されないようにするためである。終了時には元に戻す。
  - Windows Terminal で実行すると、タブが 2 つあっても、ウィンドウごと最小化される（2026-11-17、手順書のテスト 5 で確認）。ほかのタブも一緒に隠れるが、そのままとした。
- **日本語入力（IME）がオンでも、`type` と `paste` は書いたとおりに入る**（2026-11-17、手順書のテスト 6 で確認）。`type` は `KEYEVENTF_UNICODE`（キーではなく文字そのものを送る `SendInput` の指定）で送るので、IME を通らない。一方、`key` は仮想キー（キーボードのキーを表す番号）を送るので、IME を通る。メモ帳で IME をオンにして `key "a", "b", "c", "enter"` を送ると「あｂｃ」が入った。Enter は、改行ではなく変換の確定に使われたとみられる。どちらの場合も、終わったあとの IME の状態は変わらなかった。`type` の前に IME をオフにする仕組みは要らない。`key` は手で打ったときと同じふるまいなので、そのままとし、`docs/api.md` に注意を書いた。
- **ドラッグ＆ドロップで実行したときに、エラーが読めないのはそのままでよい**（2026-11-17、作成者が決めた）。exe が終わるとコンソールのウィンドウも閉じるので、エラーで終わったときもメッセージを読む間が無い（手順書のテスト 5 で確認。失敗時の画面は `logs` に残る）。ログをファイルにも書く、エラーのときはキーが押されるまで閉じない、という案もあったが、どちらも採らない。エラーを読みたいときは、コマンドプロンプトから実行すればよい。
- **テストモード（`--screen-image 画像`）を設けた**。画面の代わりに画像ファイルの中から探し、マウスやキーボードの操作は送らずにログだけを出す。自動テストのほとんどは、これで動かしている。利用者にとっても、保存された失敗時の画面を使って、見つからなかった理由を調べる手段になる。
- **見つからないときは 3 秒まで待つ**。`find`、`click`、`exists` などは、すぐに見つからなくても、既定で 3 秒まで繰り返し探す（SikuliX と同じ）。`timeout:` で変えられる。
  - **`exists` も既定で 3 秒待つ、のままとする**（2026-11-17、作成者が決めた）。`if exists("error.png")` と書くと、無いときは 3 秒かかる。すぐに結果がほしいときは、`timeout: 0` を付ける。このことは `docs/api.md` に書いてある。
- **`message_box` は API として残す**（2026-11-17、作成者が決めた）。Phase 0 の検証用に作ったものだが、スクリプトから利用者に知らせる手段として使える（SikuliX の `popup` にあたる）。
- **API の細部は、いまの書式のままとする**（2026-11-17、作成者が決めた）。`wheel :down, 3` という書き方、操作のあとの待ち時間の既定（0.2 秒）、`Pikulix.similarity = 0.8` のような既定値の変え方、`key` で使えるキーの名前などである。作成者の条件は、書式が `docs/api.md` に整理されていることである。これを受けて、`docs/api.md` を実装と突き合わせ、書かれていなかった書式を足した（`exists` と `wait_vanish` の 2 番目の引数、`wheel` の回数の省略、`offset:` を付けられるメソッド、`key` の別名と記号の扱い、`message_box` のタイトルと `exit` の終了コードの省略、待ち時間が入る操作）。
- **失敗時の画面は、exe のあるディレクトリの `logs` に保存する**。`FindFailed` になるたびに 1 枚増え、自動では消えない。
  - **自動では消さない、のままとすることを、作成者が決めた**（2026-11-17）。1 枚の大きさは、フル HD で数百 KB〜数 MB である（手順書のテスト 4 では約 593 KB。画面に写っているものによって変わる）。要らなくなったら、利用者が消す。
- **ファイルの読み書きは、`mruby-io` を入れずに自前で実装した**（2026-11-17、作成者が決めた）。案は、(1) 無しで進める、(2) 必要な分だけ自前実装、(3) 誤検知のリスクを受け入れて `mruby-io` を入れる、の 3 つだった。(3) は `WS2_32.dll` への依存が増え、誤検知を減らす方針に反する。(1) では、入力の一覧をファイルから読む、結果を書き残す、という RPA でよくある用途ができない。そこで (2) とし、範囲を小さく保った。
  - API は `read_text`、`write_text`（上書き。無ければ作る）、`append_text`（追記）、`file_exist?` の 4 つ。`File` 互換ではない。バイナリ、`Dir`、ファイルハンドルを渡す API は、需要が出るまで作らない。
  - C++ 側（`src/api.cpp`）は `CreateFileW` などのワイド文字 API で読み書きし、依存 DLL は増えていない。パスは、画像と同じくスクリプトのあるディレクトリからの相対で解決する。引数の確認は Ruby 側（`src/prelude.rb`）にある。
  - 文字コードは UTF-8 とする。読むときは UTF-8 の BOM を取り除き、UTF-16 LE（BOM 付き）は UTF-8 に変換する。Excel の「Unicode テキスト」がタブ区切りの UTF-16 LE なので、Excel で作った表をそのまま読める。UTF-8 として正しくないもの（Shift_JIS など。Excel の「CSV (コンマ区切り)」がこれにあたる）は、化けた文字列を黙って返すのではなく、エラーにする。Shift_JIS の読み込みは、要望が出たら `encoding:` のような指定を足して `MultiByteToWideChar` で変換する。
  - 書くときは BOM を付けず、改行も変換しない。
  - 表のデータは TSV（タブ区切り）を勧める（`docs/api.md`）。引用符付き CSV の解析は、需要が出たら `src/prelude.rb` に Ruby で足す。C++ 側は要らない。
- **エラーの場所は、利用者のスクリプトの行で表示する**。そのままだと `src/prelude.rb` の中の行が表示されるので、表示の前に呼び出し履歴から取り除いている。
- **終了コード**は、0 が成功、1 がスクリプトのエラー、2 が起動できなかった、3 が緊急停止である。スクリプトが `exit` を呼んだときは、その値になる。
- **操作の相手が管理者として動いているときは、警告を出す**（2026-11-17、実機での確認で追加）。管理者として動くゲームのランチャーを相手にテスト 3 を行ったところ、画像は見つかり、カーソルも動いたが、クリックが届かなかった。UIPI（権限の低いプログラムから高いプログラムへの入力を捨てる、Windows の保護の仕組み）によるものである。分かったことと、実装は次のとおり。
  - `SendInput` は、UIPI で捨てられたときも成功を返す。送った側からは、届かなかったことが分からない。ログにも `click (x, y)` と出て、終了コードも 0 になる。
  - そこで、入力を送る前に相手のウィンドウを調べる（`src/input.cpp` の `warn_if_unreachable`）。キー操作は前面のウィンドウ、マウスのボタンとホイールはカーソルの下のウィンドウを相手とみなす。カーソルの移動は届くので調べない。
  - 判定には、プロセスの「整合性レベル」（権限の高さを表す値。ふつうは 0x2000、管理者は 0x3000）を使う。相手のほうが高ければ届かない。管理者として動くプログラムの多くは、権限の低い側からは調べること自体を拒まれる（アクセス拒否）ので、それも「届かない」とみなす。実機では、ゲームのランチャーはアクセス拒否、タスク マネージャーは 0x3000 と読めた。
  - 警告は標準エラーに出し、`Pikulix.log = false` でも出る。同じウィンドウには続けて出さない。エラーにはせず、操作はそのまま送り、終了コードも変えない（判定が外れたときに、動くはずのスクリプトを止めないため）。警告のままとすることは、作成者が決めた（2026-11-17）。
  - このために使う API は `advapi32.dll` にあるので、依存 DLL が 1 つ増えた。Windows 標準の DLL である。
- **exe には、ビルドした環境のパスが含まれる**。mruby 自身の Ruby 部分に行番号を残しているためで、`vendor/mruby/mrblib/...` の絶対パス（ユーザー名を含む）が exe に入る。配布用の exe は GitHub Actions で作るので問題にならないが、手元でビルドした exe を人に渡すときは注意する。

### Phase 2 で決めたこと

公開の準備をしながら決めたこと（2026-11-17）。

- **ライセンスのファイル名は `LICENSE.txt` とした**。zip を展開した利用者が、ダブルクリックでメモ帳で開けるようにするためである。拡張子の無い `LICENSE` は、Windows では開くアプリを尋ねられる。GitHub は `LICENSE.txt` もライセンスのファイルとして認識する。サードパーティのライセンス表記も、同じ理由で `THIRD_PARTY_NOTICES.txt` とした。
- **著作権者の名前は「ぽよぽよ」とする**（2026-11-17、作成者が決め、`LICENSE.txt` を書き換えた）。はじめは、GitHub のアカウント名（`kaiwaredaikon009`）を仮に入れていた。
- **exe に組み込まれるサードパーティのものを、リンクの記録で確かめた**。`-Wl,-Map` で、リンカがどのライブラリから何を取り込んだかを書き出して調べた。静的リンクしているのは次のものである（Windows の DLL を呼ぶための取り込み用ライブラリ、`libuser32.a` などは除く）。

  | ライブラリ | 中身 | ライセンス | 表記 |
  | --- | --- | --- | --- |
  | `libmruby.a` | mruby 4.0.0 と、含めた mrbgems | MIT。ほかに、BSD 2 条項（`src/string.c` の文字列探索。表記が必要）、パブリックドメイン（`src/fmt_fp.c`、`mruby-bigint` の元になった FREE GMP）。`mruby-set` だけは、著作権者の違う MIT の `LICENSE` を持つ。 | 要る |
  | `libmingw32.a`、`libmingwex.a`、`libmsvcrt.a` | MinGW-w64 のランタイム（exe の起動処理、C の関数の一部） | ZPL 2.1 ほか。バイナリで配るときに表記を求めるものがある。そのための文書（`COPYING.MinGW-w64-runtime.txt`）が用意されている。 | 要る |
  | `libpthread.a` | winpthreads（MinGW-w64 のスレッドの実装）。gcc のスレッドモデルが `posix` なので、libstdc++ が使う。 | MIT と BSD 3 条項 | 要る |
  | `libstdc++.a`、`libgcc.a`、`libgcc_eh.a` | gcc のランタイム（C++ の標準ライブラリなど） | GPL v3 と GCC Runtime Library Exception 3.1。例外条項により、gcc でコンパイルした exe は、好きなライセンスで配れる。 | 要らない（参考として載せた） |

  - mruby のうち、`mruby-dir` の `dirent.c`（`LEGAL` に挙がっている）は、`mruby-io` と同じく含めていないので載せない。`mruby-compiler` の `y.tab.c` は bison の生成物で、bison の例外条項により、GPL は及ばない。
  - `THIRD_PARTY_NOTICES.txt` は、`vendor/mruby` の `LICENSE`、`LEGAL`、`mrbgems/mruby-set/LICENSE` と、MSYS2 の `ucrt64/share/licenses/` の `crt/COPYING.MinGW-w64-runtime.txt`、`winpthreads/COPYING` から、条文をそのまま写して作った（行末の空白だけ落とした）。gcc は 16.1.0、MinGW-w64 の crt と winpthreads は 14.0.0.r190 のものである。
  - mruby のバージョン、含める mrbgems、リンクするライブラリを変えたときは、同じ方法で見直す。GitHub Actions でビルドする環境の MSYS2 は版が違いうるが、ライセンスの条文はめったに変わらない。
- **zip の中身に、スクリプトの書き方（`docs/api.md`）も入れる**。README からの案内先であり、ネットに繋がずに読めるようにするためである。`docs/api.md` は、ほかの文書へのリンクを持たないので、単独で読める。zip の中の配置は、リポジトリと同じ `docs\api.md` とし、README のリンクがそのまま使えるようにする。zip の中身の一覧は README の「はじめかた」にある。
- **サンプルを 1 つ足した**（`samples/list_input.rb`）。一覧のファイル（`list.tsv`）を読んで 1 行ずつメモ帳に入力し、結果を `result.txt` に書き足す。ファイルの読み書きを足したので、RPA でよくある使い方の例として加えた。`result.txt` は git の管理外にした。
- **サンプルも自動テストで確かめる**（`test/samples_test.rb`）。配布物に入るので、API を変えたときにサンプルが壊れていないことを確かめるためである。テストモードで実行し、ログを突き合わせる。`hello.rb` はメッセージボックスが閉じられるまで終わらないので、文法だけを確かめる（CRuby の `RubyVM::InstructionSequence.compile_file` を使う）。

- **開発用の作業ノートも公開し、利用者向けの文書とは置き場所を分ける**（2026-11-17、作成者が決めた）。`docs/` の直下には利用者向けの `api.md` と `ビルド手順.md` だけを置き、ロードマップ、この記録、実機でのテストの手順書、開発環境のメモは `docs/dev/` に移した。`docs/dev/README.md` と各ノートの冒頭で、開発用の作業ノートであり、使うだけなら読む必要は無いことを断っている。README からも一言案内している。
  - 作業ノートを公開するかは、作成者が迷った点である。設計の記録（ADR など）、ロードマップ、手動テストの手順、`CLAUDE.md` や `AGENTS.md` を公開している OSS はふつうにあるので、公開してよいと判断した。リポジトリから外すと、複数の端末と AI のセッションでノートを共有する仕組みが別に要る。
  - 公開する前に読み返し、ユーザー名、ローカルのパス、メールアドレス、端末名、認証情報が書かれていないことを確かめた。今後も書かない（`CLAUDE.md` の作業上のルール）。
  - zip に入る `docs\api.md` の場所は変わらない。
- **公開の前に、リポジトリの履歴を 1 コミットに作り直す**（2026-11-17、作成者が決めた）。いまの履歴には、コミットの作者のメールアドレス（Gmail と、端末名から作られた仮のアドレス）と、実機での確認に使ったゲームの画面の切り抜き（`samples/target.png`、追跡を外す前のコミット）が残っているためである。作者のアドレスは、以後 GitHub の noreply アドレスにする。
  - 2026-11-17 に作成者が作り直した。古い履歴だけを書き換える方法（`git filter-repo`）もあったが、履歴は作業の記録としての価値が小さいので、作り直すほうが簡単で確実と判断した。GitHub のリポジトリも、強制 push ではなく、消して作り直した。強制 push だと、古いコミットが GitHub 上にしばらく残り、コミットの ID を知っていれば見られるためである。
  - 新しい履歴の最初の 2 コミットは、作者のアドレスが noreply ではなく、独自のダミーのアドレスになっている。個人の情報は出ていないので、そのままとした。この 2 コミットは GitHub のアカウントと結び付かない。以後の push は noreply アドレスで行う。
- **リポジトリの公開（Public）は、GitHub Actions より先に行った**（2026-11-17、作成者が決めた）。公開リポジトリなら、Actions の標準のマシンを無料で使える。非公開だと月の無料枠があり、Windows のマシンは 2 倍の速さで枠を消費する。Actions の設定は試しながら直すことになるので、先に公開した。そのため、最初の版を置くまで、README が案内する Releases は空である。

## 設計上の検討事項

### スクリプトと API

- API は SikuliX に倣い、レシーバなしのトップレベルメソッドを基本とする。名前は Ruby の慣習（snake_case）にする。
- 最初に備える機能の案:
  - 探す: `find`、`exists`、`wait`、`wait_vanish`
  - マウス: `click`、`double_click`、`right_click`、`hover`、`drag_drop`、`wheel`
  - キーボード: `type`（文字列入力）、`key`（`"ctrl+s"` のようなキー操作）、`paste`（クリップボード経由）
  - その他: `sleep`、`run`（アプリの起動）
- 見つからないときの扱いを決める。SikuliX と同じく、`find` と `click` は例外（`FindFailed`）、`exists` は `nil` を返す、とするのが分かりやすい。
- 一致度のしきい値（SikuliX の既定は 0.7）、タイムアウト、クリック位置のオフセットを指定できるようにする。
- 画像のパスは、スクリプトファイルのあるディレクトリからの相対で解決する。
- スクリプトと画像ファイル名に日本語が使えること。スクリプトは UTF-8 とし、パスはワイド文字 API で扱う。コンソール出力の文字化けにも注意する。

書き味のイメージ（案）:

```ruby
click "start_button.png"
wait "dialog.png", timeout: 10
type "こんにちは"
key "ctrl+s"

if exists("error.png")
  click "ok.png"
end
```

### 画像認識

- アルゴリズムは正規化相互相関（OpenCV の `TM_CCOEFF_NORMED` 相当）を基本とする。
- 全画面を総当たりすると遅いので、縮小画像で粗く探してから原寸で確かめる、といった高速化が要る。
- 単色に近い画像は正規化相互相関では扱えない（分散が 0 になる）ので、別の比較方法に切り替える。
- グレースケールだけで比べると、形が同じで色だけ違うもの（有効なボタンと無効なボタンなど）を区別できない。最終判定には色も使う。
- マッチング部分は画面や入力に依存しない純粋な関数にして、差し替えとテストをしやすくする。
- **自前実装を続けるかどうかは、Phase 1 で実測して判断する**。目安は、フル HD の画面で 1 回の探索が 0.2〜0.3 秒以内で、テスト画像での見落としがないこと。満たせなければ、OpenCV の静的リンクを作成者に相談する。→ 実測では目安を満たした（「Phase 1 で決めたこと」参照）。作成者が、自前実装のままとすることを決めた（2026-11-17）。
- OpenCV を使う場合、MSYS2 の出来合いパッケージは使えない。DLL 形式で、依存パッケージが 26 個、展開後 182 MB あり、単一 exe にならない。必要なモジュール（`core` と `imgproc`）だけを、ソースから静的ライブラリとしてビルドすることになる。それには CMake の導入が要る。
- 自前実装の正しさは、開発時だけ OpenCV の結果と突き合わせて確かめる方法がある。配布物には OpenCV を入れずに済む。
- PNG の読み書きは、Windows 標準の WIC か、単一ヘッダのライブラリ（stb）で行う。→ WIC にした。
- 画像の透明な部分（アルファ）は、いまは無視している。透明な部分を「何でもよい」として探す機能は無い。

### 画面キャプチャと座標

- **DPI 対応が最重要**。マニフェストで Per-Monitor V2 の DPI 対応を宣言する。宣言しないと、表示倍率が 100% でない環境で座標がずれ、キャプチャ画像も拡大縮小されてしまう。
- キャプチャは、まず GDI（`BitBlt`）で行う。速度や取りこぼしが問題になったら、DXGI Desktop Duplication を検討する。
- 座標は最初から仮想スクリーン座標で統一する。マルチモニタでは原点が負になりうる。最初の版は、プライマリモニタだけを探す対象にしてもよい。
- 画像を撮ったときと実行時とで、表示倍率・テーマ・フォントの描画が違うとマッチしない。画像認識 RPA の原理的な制約なので、README に書く。

### 入力

- マウスとキーボードは `SendInput` で送る。
- 文字列入力は `KEYEVENTF_UNICODE` で送り、キーボード配列に依存させない。SikuliX は日本語キーボードで記号がずれる問題が有名なので、同じ轍を踏まない。
- `KEYEVENTF_UNICODE` を受け付けないアプリ向けに、クリップボード経由の `paste` も用意する。クリップボードの元の内容は復元する。
- IME がオンのときに文字列入力がどうなるかは、実機で確かめる。
- **管理者権限のウィンドウには入力できない**（UIPI）。Pikulix を管理者として実行すれば回避できる。exe 自体は昇格を要求しない（`asInvoker`）。届かない相手に送ろうとしたときは、警告を出す（「Phase 1 で決めたこと」参照）。
  - 管理者として動くアプリに入力が届かないことは、このままでよい（作成者決定、2026-11-17）。そうしたアプリを操作する予定はなく、警告が出れば足りる。
- 操作の間には、短い既定の待ち時間を入れる。速すぎると操作を取りこぼすアプリがある。

### 安全装置

- **緊急停止のホットキーは最初の版から入れる**。マウスを奪われるので、止める手段がないと危険である。
- **キーは Alt+Shift+C のみとする**（作成者決定。SikuliX と同じ）。Windows のホットキー登録（`RegisterHotKey`）で実現する。
- **キーボードフックは使わない**。キーロガーと同じ仕組みなので、ウイルス対策ソフトの誤検知を増やすおそれがある。誤検知のリスクをできるだけ減らすのが作成者の方針である。
- Ctrl+C を緊急停止にする案は、次の理由で見送った。
  - どこでも効くホットキーとして登録すると、スクリプト自身が送る `key "ctrl+c"`（コピー）でも停止してしまう。
  - 人が押したものとスクリプトが送ったものを区別するには、キーボードフックが要る。
- Ctrl+C のための特別な実装はしない。コンソールにフォーカスがあるときに Ctrl+C で終了するのは、コンソールアプリの標準の動作であり、そのままにする。
- 停止時とエラー終了時には、押しっぱなしになった修飾キーとマウスボタンを必ず離す。
- 待機中やスリープ中でも、すぐ止まれるようにする。

### テンプレート画像の作り方

- SikuliX の使い勝手の核は IDE の範囲キャプチャ機能にある。画像を作る手段がないと実用にならない。
- 最初の版は、Windows 標準の Snipping Tool（Win+Shift+S）で撮って PNG で保存する運用とする。
- その次の段階で、範囲をドラッグして PNG に保存する簡易キャプチャ機能を内蔵する。IDE は作らない。

### 実行形態

- 実行は `pikulix.exe script.rb` とする。スクリプトを exe にドラッグ＆ドロップしても同じように動く。
- 終了コードを返す（成功は 0、失敗は 0 以外）。バッチファイルやタスクスケジューラから使えるようにするためである。
- コンソールウィンドウは、操作対象を隠したりキャプチャに写り込んだりしないよう、実行中は最小化する（作成者決定）。実装では、最初に画面を写し取るか入力を送るときに最小化している（「Phase 1 で決めたこと」参照）。

### ファイルの置き場所

- 設定ファイルとログは、exe のあるディレクトリの配下に置く。
- 書き込まない場所: レジストリ、`%APPDATA%`、`%LOCALAPPDATA%`、`%TEMP%`、ユーザープロファイル。
- 起動時に自己展開をしない。拡張子の関連付けなど、システムへの登録もしない。

### ログとデバッグ

- 何を探し、どこで見つけ、何をしたかを、標準出力に出す。
- 画像が見つからずに失敗したときは、その時点の画面を PNG で保存する。原因調査に必要である。
- 見つけた場所を画面上に枠で示す機能（SikuliX の `highlight`）は、後の段階とする。

### 配布

- zip の中身は、`pikulix.exe`、README、`LICENSE.txt`、サードパーティのライセンス表記（`THIRD_PARTY_NOTICES.txt`）、サンプルスクリプト、スクリプトの書き方（`docs/api.md`）とする（「Phase 2 で決めたこと」参照）。
- ビルドと zip の作成は GitHub Actions で行い、GitHub Releases に置く。exe をリポジトリにコミットしない。
- **依存 DLL の確認を受け入れ条件にする**。MinGW でビルドした exe は、何もしないと `libstdc++-6.dll` などに依存し、素の Windows では起動しない。依存先が Windows 標準の DLL だけであることを、ビルドのたびに確かめる。
- 素の Windows 11 での動作確認は、次の方法で行う。Windows サンドボックス（Pro 以上の機能）は、Home の端末では使えないので、前提にしない。
  - `objdump -p` で依存 DLL を一覧し、Windows 標準のものだけであることを確かめる（主な手段）。
  - PATH を `C:\Windows\System32` だけにして起動し、MSYS2 の DLL なしで動くことを確かめる（`rake test` に含まれる）。
  - GitHub Actions の Windows ランナーで起動を確かめる（Phase 2 以降）。
  - Pro の端末では、Windows サンドボックスでも確かめられる（`rake sandbox`）。公開前に 1 回は行いたい。
- 署名のない exe は、SmartScreen の警告が出る。また、画面キャプチャと入力送信を行うプログラムは、ウイルス対策ソフトに誤検知されやすい。当面は README に明記して対処し、コード署名は将来の検討とする。

### ライセンスと公開リポジトリ

- 同梱するライブラリのライセンス表記を、配布物に含める（mruby は MIT）。依存を足す前に、ライセンスと、静的リンクで単一 exe を保てるかを確認する。表記は `THIRD_PARTY_NOTICES.txt` にまとめた。mruby のほか、gcc と MinGW-w64 のランタイムも exe に入っている（「Phase 2 で決めたこと」参照）。
- README は日本語を主とし、英語の概要を添える（作成者決定）。
- SikuliX とは無関係の独立した実装であることを、README に書く。SikuliX のコードやロゴは流用しない。
- 公開リポジトリなので、個人情報の写ったスクリーンショットや認証情報をコミットしない。テスト用の画像は、専用に作ったものを使う。

### 既知の制約

README にも書く。

- 対話的なデスクトップが必要である。ロック画面、切断したリモートデスクトップ、UAC の確認画面では動かない。
- 管理者権限のウィンドウは、管理者として実行しないと操作できない。
- 著作権保護されたコンテンツなどは、黒くキャプチャされることがある。
