# ビルド手順

Pikulix を自分でビルドするための手順である。使うだけなら、ビルドは要らない。

## 必要なもの

Windows 10 / 11（x64）で、次の 2 つが要る。

- **Git**
- **RubyInstaller の「Ruby+Devkit」版**（x64）。<https://rubyinstaller.org/> から入手する。

Ruby+Devkit には、Ruby と一緒に MSYS2 が入っている。MSYS2 は、Linux でおなじみの gcc などを Windows で使えるようにした道具一式である。Pikulix はこの gcc（UCRT64 という系統のもの）でコンパイルする。

Visual Studio、CMake、.NET SDK は要らない。

確認済みの組み合わせは、Ruby 4.0.5 と gcc 16.1.0 である。

### gcc が入っているかの確認

```
ridk exec gcc --version
```

バージョンが表示されればよい。`ridk` は RubyInstaller に付属するコマンドで、MSYS2 の道具を呼び出すのに使う。

見つからないと言われた場合は、次のコマンドで MSYS2 の開発ツールを入れる。選択肢を聞かれたら、そのまま Enter を押せばよい。

```
ridk install
```

## ビルド

リポジトリのディレクトリで、次を実行する。

```
rake
```

これだけで、次のことが行われる。

1. mruby 4.0.0 のソースを `vendor/mruby` に取得する（初回のみ。`git clone` を使う）。
2. mruby をコンパイルして、ライブラリ（`build/mruby/host/lib/libmruby.a`）を作る。
3. `src/` をコンパイルし、mruby と合わせて `build/pikulix.exe` を作る。
4. exe の依存 DLL が Windows 標準のものだけであることを確かめる。

初回は 1 分ほどかかる。2 回目からは、変更のあったところだけがコンパイルされる。

gcc への PATH を通しておく必要はない。PATH に gcc が無ければ、`Rakefile` が RubyInstaller 付属の MSYS2 を自動で使う。

## 動かしてみる

```
build\pikulix.exe samples\hello.rb
```

メッセージボックスが表示されれば成功である。

スクリプトの書き方は [api.md](api.md) にある。`samples/` には、ほかに次のサンプルがある。

- `samples/notepad.rb`: メモ帳を開いて文字を入力する。画像は使わない。
- `samples/list_input.rb`: 一覧のファイル（`samples/list.tsv`）を読んで、1 行ずつメモ帳に入力し、結果を `samples/result.txt` に書き足す。画像は使わない。`result.txt` は git の管理外である。
- `samples/click_image.rb`: 自分で切り取った画像を探してクリックする。

これらは実際にマウスやキーボードを動かす。途中で止めたいときは、Alt+Shift+C を押す。

## rake のタスク

| コマンド | すること |
| --- | --- |
| `rake` | `build/pikulix.exe` をビルドし、依存 DLL を確かめる。 |
| `rake test` | ビルドしてから、画面を使わないテスト（`test/run.rb`）を実行する。 |
| `rake bench` | 画像を探す処理の所要時間をはかる（画面は使わない）。 |
| `rake check_deps` | 依存 DLL の確認だけを行う。 |
| `rake sandbox` | Windows サンドボックスで確かめるためのファイルを用意する（任意。後述）。 |
| `rake package` | 配布用の zip（`build/pikulix-バージョン.zip`）を作る（後述）。 |
| `rake version` | バージョン（`src/version.h`）を表示する。 |
| `rake mruby:build` | mruby だけをビルドし直す。 |
| `rake clean` | `src/` から作ったものを消す。mruby のビルド結果は残す。 |
| `rake clobber` | `build/` をすべて消す。 |

## テストについて

`rake test` は、`build/pikulix.exe` を実際に起動して、出力と終了コードを確かめる。実際の画面は使わず、マウスやキーボードも動かさないので、作業中の端末でも実行できる。

| ファイル | 確かめること |
| --- | --- |
| `test/host_test.rb` | スクリプトを読んで実行する部分（日本語、エラーの表示、終了コード）。 |
| `test/match_test.rb` | 画像を探す処理。小さな画像では、すべての場所の一致度を Ruby で計算して突き合わせる。 |
| `test/api_test.rb` | スクリプト API。 |
| `test/file_test.rb` | ファイルの読み書き（`read_text` など）。 |
| `test/samples_test.rb` | `samples/` のサンプルスクリプト。配布物に入るので、テストモードで実行して、壊れていないことを確かめる。 |

画像を使うテストは、exe のテストモード（`--screen-image`）で動かす。画面の代わりに画像ファイルの中から探し、マウスやキーボードの操作は送らずにログだけを出すモードである。

テスト用の画像は、実際の画面を写したものではなく、`test/support/canvas.rb` がその場で描いて作る（`build/test/` に置かれる）。公開リポジトリに、個人情報の写った画像を入れないためである。

実際の画面のキャプチャと、マウス・キーボードの操作は、自動テストでは確かめていない。`samples/` のスクリプトを動かして確かめる。

## 依存 DLL の確認について

MinGW 系の gcc で作った exe は、何もしないと `libstdc++-6.dll` などの DLL に依存し、gcc の入っていない Windows では起動しない。Pikulix は静的リンク（必要なライブラリを exe の中に取り込む方法）でこれを避けている。

`rake` は、ビルドのたびに exe の依存先を調べる。`Rakefile` の `ALLOWED_DLLS` に無い DLL に依存していると、ビルドは失敗する。新しい Win32 API を使って依存先が増えたときは、それが Windows 標準の DLL であることを確かめてから `ALLOWED_DLLS` に足す。

## 素の Windows での確認

開発ツールの入っていない Windows でも exe が動くことは、次の 2 つで確かめている。どちらも自動で、Windows のエディションを問わない。

- 依存 DLL の確認（前述）。
- `rake test` が、PATH を `C:\Windows\System32` だけにして exe を起動する。gcc 付属の DLL が見つからない状態になるので、それらに依存していれば失敗する。

### Windows サンドボックスで確かめる（任意）

Windows サンドボックスは、使い捨てのまっさらな Windows を、ウィンドウの中で起動する機能である。開発ツールの入っていない環境で exe が動くことを、実際に確かめられる。Windows 11 の Pro 以上で使える（Home では使えない）。必須ではない。

#### 有効にする（初回のみ）

1. スタートメニューで「Windows の機能の有効化または無効化」を検索して開く。
2. 「Windows サンドボックス」にチェックを入れて OK を押す。
3. 再起動する。

#### 確かめる

```
rake sandbox
```

`build/sandbox/` に、exe とサンプルスクリプト、サンドボックスの設定ファイル（`pikulix.wsb`）が作られる。`pikulix.wsb` をダブルクリックすると、サンドボックスが起動し、exe の入ったフォルダが開く。

その中で `hello.rb` を `pikulix.exe` にドラッグ＆ドロップし、メッセージボックスが出ることを確かめる。日本語のファイル名（`こんにちは.rb`）でも同じように試す。

サンドボックスは、ウィンドウを閉じると中身がすべて消える。

## 配布用の zip

```
rake package
```

ビルドしてから、`build/pikulix-0.1.0.zip` のような zip を作る。中身は README の「はじめかた」にある一覧のとおりで、zip の直下に置く（フォルダに入れない）。Windows 標準の「すべて展開」は、zip と同じ名前のフォルダを作ってそこへ展開するので、中にもフォルダがあると二重になるためである。

- `samples/` などは、git で管理しているファイルだけを入れる。手元にある管理外のファイル（`samples/result.txt` など）は入らない。
- コミットしていない変更があると、注意を表示する。zip には、そのときのファイルが入る。
- zip は、Windows に付属の `tar.exe` で作る。

公開する zip は、手元では作らず、GitHub Actions で作る（次節）。

## GitHub Actions

GitHub Actions は、push などをきっかけに、GitHub が用意したマシンでコマンドを実行する仕組みである。設定は `.github/workflows/build.yml` にある。

| きっかけ | すること |
| --- | --- |
| `main` への push、pull request | Windows のマシンで `rake test` と `rake package` を行う。zip は、実行結果のページの「Artifacts」からダウンロードできる。 |
| `v` で始まるタグ（`v0.1.0` など）の push | 上に加えて、タグと `src/version.h` のバージョンが一致することを確かめ、Releases に**下書き**を作って zip を置く。 |

マシンには、手元と同じく RubyInstaller の Ruby と付属の MSYS2 を入れる（`ruby/setup-ruby`）。gcc の版は手元と違いうるので、実行結果に記録している（「gcc の版を記録する」の手順）。

実行結果は、リポジトリの「Actions」タブで見られる。

## リリース

1. `src/version.h` のバージョンを書き換え、コミットして `main` に push する。Actions のビルドが通ることを確かめる。
2. タグを付けて push する。

   ```
   git tag v0.1.0
   git push origin v0.1.0
   ```

3. Actions が終わると、Releases に下書きができる。下書きは、リポジトリの持ち主にしか見えない。
4. 下書きの zip をダウンロードして確かめる（`docs/dev/人が行うテスト手順書.md` のテスト 10）。
5. 下書きを編集し、「変更点」を書いて公開する（「Publish release」）。

下書きの zip に問題があったときは、下書きとタグを消し、直してから 1. からやり直す。タグは次のように消す。

```
git tag -d v0.1.0
git push origin :refs/tags/v0.1.0
```

公開したあとの版は、作り直さない。直すときは、バージョンを上げて出し直す。

## mruby の設定を変えるとき

- 取り込む mruby のバージョンは、`Rakefile` の `MRUBY_TAG` と `MRUBY_COMMIT` で固定している。
- スクリプトから使える機能（mrbgems）は、`mruby_build_config.rb` で決めている。
- mruby のコンパイル時の定義（`MRB_UTF8_STRING` など）は、`mruby_build_config.rb` と `Rakefile` の `MRUBY_DEFINES` の両方に書く。食い違うと、原因の分かりにくい不具合になる。
- mruby のバージョンや、含める mrbgems、リンクするライブラリを変えたときは、`THIRD_PARTY_NOTICES.txt`（exe に組み込んだもののライセンス表記）を見直す。何を見て作ったかは、`docs/dev/設計と調査の記録.md` の「Phase 2 で決めたこと」にある。
